# Source research: what to borrow from Traycer's references

Research snapshot: November 26, 2026. “Direct” means the source body or repository documentation was readable. Search excerpts and Traycer's own account are marked separately. Vendor case studies describe their own environments; none establishes a likely result for our team.

| Source | Finding | Design decision |
| --- | --- | --- |
| [Traycer: How to build a software factory](https://traycer.ai/blog/how-to-build-a-software-factory), direct | One job before many; evidence before autonomy; read access separated from posting. Their LLM message filter held approval requests. They disclose a Windows verification gap even for a successful fix. | Require machine-produced receipts and explicit coverage gaps. Use rule-based notifications and budgets. No agent write keys, auto-merge, or claims about environments that did not run. |
| [Matt Pocock's skills](https://github.com/mattpocock/skills), direct repository README | `grill-with-docs` captures vocabulary and durable decisions; `to-spec` synthesizes aligned intent; `to-tickets` cuts a spec into runnable slices with dependency edges; `retro` proposes improvements to the environment. | Use a short intent card and explicit acceptance criteria. Keep durable decisions in ADRs, not every planning transcript. Break the rollout into complete, demonstrable slices. Borrow the practices, not auto-updating plugins in a trusted workflow. |
| [Dex Horthy's series, part 1](https://x.com/dexhorthy/article/2080697380379427275), [part 2](https://x.com/dexhorthy/article/2081058573556306030), [part 3](https://x.com/dexhorthy/status/2081797628552270027), partial | Indexed excerpts support the critique of lights-off codebase maintenance and a lights-on alternative. The detailed review stages come from Traycer's account; the original full series was not reliably accessible. | Separate reviews of product intent, system boundaries, and implementation shape where risk warrants it. Human owners still review code whose maintainability matters. |
| [Lauren Tan's pstack](https://github.com/cursor/plugins/tree/main/pstack), direct README; [trust pyramid post](https://x.com/poteto/status/2111133080526495985), via Traycer | Verification skills map behaviors to real app checks; formal verification targets a specific property; the PR playbook checks each code-ready head. Traycer attributes “architecture, static checks, prose, review” to the trust pyramid. | Prefer mechanically enforced boundaries over prompt rules. Maintain a small behavior-to-check index. Invalidate old receipts after patch or head changes. |
| [GitHub Next / Microsoft Research: PDD Kit](https://githubnext.com/projects/pdd-kit/), direct follow-up to the linked announcement | Human-approved intent and trusted assumptions precede implementation. The Verus-based research prototype verifies Rust against a spec and distinguishes proof, tests, and assumptions. Deliberately bad variants help catch weak specs. | Borrow the receipt format and negative fixtures. The Rust pilot does not add Verus or describe empirical evidence as proof. |
| [Leslie Lamport: TLA+](https://lamport.azurewebsites.net/tla/tla.html), direct | A way to model concurrent or distributed behavior. Checking the model is not checking the implementation. | Consider modeling approval revocation, duplicate publication and cancellation only if the publisher warrants it; test those interleavings at the real boundaries regardless. |
| [Sandcastle branch strategies](https://github.com/mattpocock/sandcastle/blob/main/docs/guide/branch-strategies.md), direct | Branch strategies and sandbox providers are separate choices. The documented Docker bind-mount path exposes the worktree and parts of Git metadata; defaults can modify or merge back into the host checkout. | Use Sandcastle as a reference for runner adapters. Do not inherit checkout/write-back defaults. A worktree is not a credential or process boundary. Export a patch from a disposable guest, not a mutable checkout. |
| [Zach Lloyd: Crawl, walk, run](https://warp.dev/blog/adopting-the-software-factory-model-crawl-walk-run), direct author article | Start with discrete jobs, then connect the lifecycle on a simple product. Coordination and shared telemetry start paying off when isolated automations multiply. | Manual single job first, approved publication second, more triggers after the team has review capacity. Keep the issue tracker as the user interface. |
| [The Pragmatic Engineer: Inside OpenAI's agentic software factory](https://newsletter.pragmaticengineer.com/p/openai-software-factory), paid, accessible extract only | The extract establishes interview context but not details such as specialist reviews or production alerts. Those details are attributed to Traycer's summary, not independently confirmed from the interview. | Use the separate engineering write-ups below for corroborating patterns, not for claiming the same internal systems. |
| [OpenAI: Harness engineering](https://openai.com/index/harness-engineering/) and [Symphony](https://openai.com/index/open-source-codex-orchestration-symphony), direct corroborating sources | The first describes a short `AGENTS.md` index, versioned knowledge, mechanical boundaries, and isolated app-level QA. The second describes issue-driven scheduling, bounded concurrency, recovery, and follow-through on CI. Symphony's draft spec does not mandate our sandbox policy. | Use a maintained repository map, stable issue identity and fresh evidence for each PR head. Do not inherit direct agent write access or team-specific merge practices. |
| [Warp: Self-improving factories](https://www.warp.dev/blog/agent-self-improving-software-factories) and [Factory Benchmarks](https://warp.dev/blog/warp-factory-benchmarks), direct author/company material related to the Holmes links | Versioned configuration makes prior tasks replayable. Scorers help diagnose failure patterns; paired runs on the same tasks test proposed improvements. Warp reports a cost reduction on specific tasks; the numbers differ across Warp's post and Traycer's account and should not be pooled. | Record recipe, runner, and model revisions. Use redacted replay cases, an untouched holdout, and a human-reviewed config diff. Model scores are advisory, not authorization. |

Other linked X material, including Theo's babysitting prompt, individual Holmes and Tan posts, and the Huntley framing, was not relied on for independently verified claims. Where the original social posts were not readable, the table points to author or organization material that was. The earlier [stack comparison](../adr/001-software-factory-design.md#stack-and-adoption-evidence) separates survey familiarity from capability fit.
